\[
\boxed{
\text{Memory-R1}

不训练新的 extractor/retriever，也不实现 Memory-R2 的 local rerollout。

整体保持：

```text
Dialogue turn
    -> 原有 Fact Extractor
    -> Memory Manager
    -> Memory Bank M_t

Question + Memory Bank
    -> 冻结 Answer Agent
    -> answer y_M

Original dialogue + question
    -> 训练期 Oracle Evaluator
    -> evidence / memory coverage

answer reward + evidence reward
    -> PPO / GRPO 更新 Memory Manager
```

关键约束是：原始对话不能进入真正的 `Answer Agent` 输入。否则 Answer Agent 可以绕过 memory，manager 得不到有效训练信号。

## 最终训练变量

对第 \(t\) 个 turn：

\[
M_{t+1}=T(M_t,a_t)
\]

其中：

\[
a_t=(o_t,m'_t)
\]

manager 只基于：

\[
a_t\sim\pi_\theta(a_t\mid x_t,M_t)
\]

进行决策。

Answer Agent 输入：

\[
(q,M_\tau)
\]

生成：

\[
y_M\sim\pi_A(y\mid q,M_\tau)
\]

其中 \(\pi_A\) 训练初期冻结。

Oracle Evaluator 输入：

\[
(q,D_{\leq \tau})
\]

输出回答问题所需的原始 evidence：

\[
E_q
\]

并通过 memory 的 `source_turn_ids` 判断这些证据是否被保存。

## Reward 设计

最终 QA reward 保持 Memory-R1 的主逻辑：

\[
R_{\mathrm{QA}}
=
\operatorname{EM}(y_M,y^\star)
\]

然后利用原始对话和 evidence 构造每个 turn 的状态价值：

\[
\Phi_t(q)
=
\frac{
|E_{q,\leq t}\cap \operatorname{Sources}(M_t)|
}{
|E_{q,\leq t}|
}
\]

其中：

\[
E_{q,\leq t}=E_q\cap D_{\leq t}
\]

这样不会奖励 manager 提前保存尚未出现的信息。

逐步 shaping reward：

\[
r_t^{\mathrm{dense}}
=
\gamma\Phi_{t+1}(q)-\Phi_t(q)
\]

最终用于训练的 reward：

\[
r_t=
\begin{cases}
\eta r_t^{\mathrm{dense}}, & t<\tau\\[4pt]
R_{\mathrm{QA}}+\eta r_t^{\mathrm{dense}}, & t=\tau
\end{cases}
\]

其中 \(\eta\) 控制 evidence reward 的强度。

如果某个 `UPDATE` 把关键证据合并进 memory：

\[
\Phi_{t+1}>\Phi_t
\]

它立即得到正 reward。

如果某个 `DELETE` 删除了之后需要的证据：

\[
\Phi_{t+1}<\Phi_t
\]

它立即得到负 reward。

这就是第二阶段优化的核心。

## 需要改动的代码部分

现有 R1 结构中，主要需要改 5 个地方：

1. `MemoryEntry`
   - 增加 `source_turn_ids`
   - 记录 memory 来自哪些原始对话 turn

2. `MemoryBank`
   - 每次 `ADD/UPDATE/DELETE` 保存前后状态
   - 形成：
     \[
     (M_t,a_t,M_{t+1})
     \]

3. 数据构造
   - 保存 QA 对应的 evidence turn ids
   - 或使用训练期 Oracle Evaluator 生成 evidence

4. Reward Manager
   - 除最终 QA reward 外，计算 \(\Phi_t\)
   - 输出 turn-level reward

5. PPO/GRPO 训练入口
   - 不再只对整条 manager response 使用一个 reward
   - 根据每个 turn 的 reward 计算 return / advantage

最终不需要改：

- extractor 的模型结构
- retriever 的训练方式
- Answer Agent 的模型结构
- memory operation 的动作空间

## 这个方案能解决到什么程度

它可以明显改善：

- manager 的动作和 reward 之间的时间距离
- memory 是否保存了原始证据的可解释性
- `ADD/UPDATE/DELETE` 的局部信用分配
- memory 丢失和 answer 错误之间的诊断

但它仍然不能完全解决：

- 多个 rollout 之间 memory 状态不同造成的 GRPO 比较偏差
- 离散 memory operation 的不可微问题
- 长期 memory action 对多个未来 QA 的精确归因

所以论文贡献可以准确表述为：

> We improve Memory-R1 with privileged raw-dialogue evidence supervision and potential-based per-turn reward shaping for memory management.

而不是声称完全解决 long-horizon credit assignment。

实验上建议至少做三组：

\[
\text{R1 baseline}
\]

\[
\text{R1 + terminal QA reward}
\]

\[
\text{R1 + terminal QA reward + evidence-aware dense reward}
\]

这样能够清楚证明提升来自原始对话辅助的 credit assignment，而不是模型规模或检索变化。

但当前代码不能直接加一个 `--lora` 参数就运行：

- [train_answer_grpo.py](C:/project/mythesis/memory_r1_reproduction/scripts/train_answer_grpo.py:194) 当前加载完整 actor 和 reference。
- [train_manager_grpo.py](C:/project/mythesis/memory_r1_reproduction/scripts/train_manager_grpo.py:358) 当前同时加载完整 Manager、reference、Answer Agent。
- 两个脚本都把 `actor.parameters()` 交给 AdamW。
- 当前没有 `peft`、`bitsandbytes` 或 adapter checkpoint 加载逻辑。

需要修改的关键点：

1. actor 使用 LoRA，optimizer 只接收 LoRA 的可训练参数。
2. reference 保持冻结的 base model，不加载 actor 的 LoRA adapter。
3. Manager 训练时 Answer Agent 继续完全冻结。
4. Answer Agent 和 Manager 的 checkpoint 改为 adapter checkpoint；后续加载时必须先加载 base model，再用 `PeftModel.from_pretrained()` 加载 adapter。PEFT 官方文档明确说明，adapter checkpoint 不能脱离 base model 单独使用。[PEFT adapter 加载文档](https://huggingface.co/docs/peft/main/tutorial/peft_model_config)
5. 如果用 QLoRA，模型必须以 4-bit 加载，并且只能训练额外参数；这正是 bitsandbytes 官方支持的训练方式。[Transformers bitsandbytes 文档](https://huggingface.co/docs/transformers/main/quantization/bitsandbytes)

最重要的资源问题是：**LoRA 本身主要减少梯度和 optimizer 显存，不会自动减少 base model 权重显存。**

当前 Manager 训练大致同时需要：

```text
Manager actor
Manager reference
Answer Agent
```

如果三份都是 20B bf16，仅权重就可能接近 120 GB，还没有算 activation、KV cache 和 optimizer。因此：

```text
LoRA：减少训练状态显存
QLoRA：进一步减少模型权重显存
```

对你现在的 20B 模型，比较现实的方案是：

```text
Answer Agent: QLoRA + GRPO
Memory Manager: QLoRA + GRPO
Reference: 4-bit frozen base model
Answer Agent reward model: 4-bit frozen model
num_generations: 2
epochs: 1
max_new_tokens: 128 或 256
LoRA rank: 8
```

但这有一个前提：当前 `gpt-oss-20b` 的 Transformers 模型结构必须能被当前版本的 `bitsandbytes + PEFT` 正常加载。这个不能从论文或模型名推断，必须实际做一次加载测试。

我的判断是：

- **不建议换 DPO。**
- **建议保留 GRPO。**
- **建议采用 QLoRA + GRPO，而不是只采用 LoRA + GRPO。**
- **先只训练一个 Answer Agent 小样本 smoke test，再训练 Manager。**
- **论文中应称为“parameter-efficient Memory-R1”或“QLoRA-based Memory-R1”，不要称为原论文严格复现。**

另外，训练开始前要关闭占用同一块 GPU 的 vLLM 数据生成服务，否则 QLoRA 仍可能因为显存不足启动失败。
